# Rewrite Bubble Task in Rails 8 (Hotwire + SQLite + Kamal)

## Context
Bubble Task is currently split in two:
- `api/`: Express, Passport sessions and MongoDB, hosted on Heroku.
- `web/`: CRA React 17, hosted on Netlify.

Most of `web/src/App.js` (on `main`) is hand-written `fetch` plumbing that keeps React state in sync with the API. The cross-origin setup also forces CORS and cross-site session cookies. The API has gaps too: task/worker update and delete are not scoped to the owner (any logged-in user can modify anyone's records by ID), and reordering sends one PUT per item.

The goal is a single Rails 8 app with these choices (all confirmed with the user):
- **Frontend:** Hotwire (server-rendered ERB, Turbo Streams for updates, Stimulus for interactivity).
- **Database:** SQLite.
- **Deployment:** Docker image deployed with Kamal to a small VPS.
- **Data:** start fresh, with no Mongo migration.

## Setup
- Branch `rails-rewrite`. Ruby isn't needed on the Mac, so generate the app from a throwaway container:
  `docker run --rm -v "$PWD":/rails -w /rails ruby:<current stable> sh -c "gem install rails && rails new . --name=bubble_task --database=sqlite3 --skip-action-mailbox --skip-action-text --skip-active-storage"` (Rails 8.x).
- As the branch's first commit, delete the old code: `api/`, `web/`, the root `index.html` and `notes.md`. It stays readable on `main`, so the CSS, favicon and `Bubble.js` logic can be ported with `git show main:<path>`.
- **Local dev runs in docker compose.** The generated `Dockerfile` stays production-only (Kamal uses it). Add separate dev files:
  - `Dockerfile.dev`: the same `ruby` slim base image as the generated `Dockerfile`, plus the packages needed to build gems and `sqlite3`. Gems aren't baked into the image: the `web` service runs `bin/setup`, which installs them (dev and test included) into the `bundle` volume, prepares the database and starts the server.
  - `compose.yml`:
    - **`web` service:**
      - builds `Dockerfile.dev`
      - bind-mounts `.:/rails`, plus a named volume `bundle:/usr/local/bundle` so gems survive rebuilds
      - publishes port `3000:3000`, runs `bin/setup` with `BINDING=0.0.0.0`, and keeps the pidfile on a `/tmp` tmpfs
      - sets `stdin_open: true` and `tty: true` so `docker compose attach web` reaches `debugger` breakpoints
      - SQLite files live in `storage/` on the bind mount (already gitignored)
    - **`chrome` service:** the `selenium/standalone-chromium` image (pinned tag) for system tests. When `SELENIUM_HOST` is set, `ApplicationSystemTestCase` drives that remote browser and uses `served_by host: "web"` so the browser can reach the test server.
- Daily commands:
  - start the app: `docker compose up -d`
  - everything else: `docker compose exec web bin/rails …` (console, migrations, tests)
  - after a Gemfile change: `docker compose restart web` (`bin/setup` re-runs `bundle install`)

## Data model
| table | columns | notes |
|---|---|---|
| users | `email_address` (unique index, normalized with `strip.downcase`), `password_digest`, `guest` bool | Guests get a placeholder email (`guest-<hex>@guest.invalid`) and a random password they never see, so every column is required and all validations apply to everyone |
| sessions | generated by the Rails auth generator | |
| workers | `user_id` FK, `name`, `position` | `belongs_to :user`, `has_many :tasks` |
| tasks | `user_id` FK, `worker_id` FK (nullable), `name`, `position`, `percent_complete` int (0/25/50/75/100) | validate inclusion of `percent_complete`, and that `worker` belongs to the same user |

Domain logic moves into the models:
- **`Task#advance!(worker)`** (named for what happens to the task; "click" stays in the controller) ports the cycle from `web/src/components/Bubble.js` lines 62–76 (on `main`):
  - unassigned → assign the worker at 0%
  - assigned to this worker → add 25%
  - past 75% → unassign
  - assigned to a different worker → no-op
- **Worker `before_destroy`:** runs `tasks.update_all(worker_id: nil, percent_complete: 0)`. This matches the frontend's behaviour; the old API reset only `assignedTo`, so the two disagreed.
- **`Positioned` concern**, shared by both models:
  - `reposition(ids)`: a class method that sets `position` from an ordered ID array in one transaction. Not named `reorder`, which is a built-in Active Record query method. It doesn't use `Current`: call it through the association (`Current.user.tasks.reposition(ids)`) and the association's scope makes it ignore other users' IDs.
  - New records go to the end of their user's list (`before_create`).
  - `User`'s `has_many :workers` and `has_many :tasks` are ordered by `position`.

- **Mail delivery:**
  - development: use the `letter_opener_web` gem, mounted at `/letter_opener`. Plain `letter_opener` can't open a browser from inside the container.
  - production: SMTP through a transactional provider (Resend, Postmark or SES), with credentials in `config/credentials.yml.enc`
  - set `config.action_mailer.default_url_options = { host: <domain> }` and a `from` address on the domain, with SPF/DKIM DNS records from the provider

### Sandbox mode, replacing the client-only sandbox in App.js
- **Guests are ordinary users** with `guest: true`, so `Current.user.workers` and every controller work the same for them. No session- or cookie-stored sandbox.
- **Created on request, never by a page view.** A logged-out visit to `/` still redirects to the log-in page, which gets a **"Try it out"** button: `button_to` a `POST` to `GuestsController#create` (`resource :guest, only: :create`). GET requests stay side-effect free, so bots and crawlers create nothing.
- **`User.create_guest!`** (a class method, not a callback) creates the guest with a placeholder email (`guest-#{SecureRandom.hex(8)}@guest.invalid`; `.invalid` is a reserved domain that can never receive mail) and a random password (`SecureRandom.base58(24)`), and seeds the old demo data (workers Jack and Jill, tasks Build and Sell) in one transaction. The controller then starts a normal session.
- **Signing up while a guest converts that guest:** it replaces both placeholders with the email and password they enter, and sets `guest: false`, so sandbox work is kept. This is an improvement over the old app, which lost it.
- **Logging in while a guest abandons the guest record.**
- **Guests' placeholder emails stay out of sight:** the nav shows "Guest" instead, and password reset skips guests (`unless user.guest?`), so no mail is ever sent to a `.invalid` address. Anything that later lists or emails users must leave guests out: add a `registered` scope (`where(guest: false)`) with the first query that needs it, not before.
- A Solid Queue recurring job (`config/recurring.yml`) runs hourly and deletes guest users older than 24 hours (`User::GUEST_LIFETIME`), along with their dependent records. The board tells guests how many hours are left, counted to the job's actual run (`User#deletion_time`). Since guests only exist when someone clicks "Try it out", this is routine tidying.

## Routes and controllers
```ruby
root "boards#show"
resource  :session
resource  :registration, only: %i[new create]
resource  :guest,        only: :create   # GuestsController: "Try it out"
resources :workers, only: %i[create destroy]
resources :tasks,   only: %i[create destroy] do
  resource :progress, only: :update, module: :tasks  # Tasks::ProgressesController, params: worker_id
end
resource :worker_order, only: :update  # WorkerOrdersController, params: ids[]
resource :task_order,   only: :update  # TaskOrdersController,   params: ids[]
```
- Only standard RESTful actions. Clicking a bubble and reordering are their own resources rather than custom actions, as `CLAUDE.md` requires.
- Every lookup goes through `Current.user.workers` or `Current.user.tasks`, which closes the owner-scoping hole.
- Every action responds with a single `turbo_stream.replace "board"` that re-renders the grid partial. The grid is tiny, so finer-grained streams aren't worth the complexity.

## Views and frontend
- `boards/show.html.erb` contains:
  - the nav (log in, sign up, log out)
  - the welcome text for guests
  - two `form_with` add forms
  - `_board.html.erb` (the table), wrapped in `id="board"`
  - the how-to list
- **Bubbles:** each bubble is a `button_to task_progress_path(task, worker_id:), method: :patch`, styled with the existing `bubble-00` … `bubble-100` and `bubble-na` classes.
- **Stimulus `sortable_controller`:**
  - ports the native HTML5 drag-and-drop from `Header.js` and `Trash.js`
  - on a drop onto an item of the same kind, sends `PATCH` to `worker_order_path` or `task_order_path` with the new ID order
  - on a drop onto the trash, sends `DELETE`
  - uses `@rails/request.js` (via importmap), which handles the CSRF token and applies Turbo Stream responses automatically
- **Styles:** port `web/src/App.css` and `web/src/index.css` from `main` to `app/assets/stylesheets/`. Copy the Font Awesome `<link>` and the favicon from `web/public/` on `main`.

## Deployment (Kamal)
- Provision a small VPS (Hetzner or DigitalOcean, about $5/mo) and point a domain's A record at it.
- In `config/deploy.yml`:
  - server IP
  - image registry (GHCR or Docker Hub)
  - `proxy: { ssl: true, host: <domain> }`
  - keep the generated `bubble_task_storage:/rails/storage` volume, which is where the SQLite files live
- Secrets: put `RAILS_MASTER_KEY` and `KAMAL_REGISTRY_PASSWORD` in `.kamal/secrets`. The SMTP credentials live in Rails credentials, which the master key unlocks.
- Create an account with the mail provider, verify the sending domain and add its DNS records before the first deploy.
- Leave `SOLID_QUEUE_IN_PUMA=true` (the default) so the cleanup job runs without a separate worker.
- Run `kamal setup` once, then `kamal deploy` for each release.
- Optional later step: Litestream sidecar (Kamal accessory) to back up SQLite to S3-compatible storage.
- After cutover, shut down the Heroku app and the Netlify site.

## Verification
Tests ship in the same PR as the code they cover. CI (the generated GitHub Actions workflow: tests, system tests, RuboCop, Brakeman) must pass before a PR merges. Use Minitest with fixtures, the Rails default. Keep system tests few, covering only the browser interactions (clicks, drag and drop), and test logic at the model and integration levels.

- **Model tests** (Minitest):
  - `Task#advance!` covers every state transition, including a click on a different worker
  - destroying a worker unassigns its tasks and resets them to 0%
  - `reposition` (called through an association) ignores IDs belonging to other users
- **Integration tests:**
  - CRUD as user A cannot touch user B's records (404)
  - guest-to-signup conversion keeps the sandbox data
  - "Try it out" creates a seeded guest and logs them in; a logged-out GET creates nothing
  - sign-up rejects a duplicate email (regardless of case) or an invalid one
  - password reset sends an email (`assert_emails`), and the token link sets a new password
- **System test** (Capybara and Selenium): click a bubble through its full cycle, add a worker and a task, and drag one to the trash.
- **Running tests:** `docker compose exec web bin/ci` runs every check (the steps in `config/ci.rb`, matching GitHub Actions). For just the tests: `bin/rails test` for model and integration tests, and `bin/rails test:system` for system tests, which run against the `chrome` service.
- **Manual:** run `docker compose up` and open http://localhost:3000. Go through the whole how-to list, request a password reset and check it at `/letter_opener`, and test a `debugger` breakpoint with `docker compose attach web`. Run `kamal deploy`, check HTTPS on the domain, and confirm a real reset email arrives.
